# Contributing to sezgi

Thank you for your interest in sezgi. This document covers how to set up a
development environment, the conventions the project holds itself to, and
what a pull request is expected to include.

## Development setup

sezgi's core is Rust (`crates/`), with thin, class-first frontends in
Python (`py-sezgi/`) and R (`r-sezgi/`). All three share one native
implementation — there is no separate reimplementation per language.

### Prerequisites

- A [Rust toolchain](https://rustup.rs/) (stable channel).
- Python >= 3.9 if you are working on the Python frontend or docs.
- R >= 4.0 if you are working on the R frontend.

### Python (uv-first)

This project uses [`uv`](https://docs.astral.sh/uv/) exclusively for
Python tooling — no bare `pip`/`venv`. From the repository root:

```bash
uv venv py-sezgi/.venv
uv pip install --python py-sezgi/.venv/bin/python maturin
cd py-sezgi
uv run --python .venv/bin/python maturin develop --release
```

`maturin develop --release` compiles the Rust extension (`sezgi._sezgi`)
and installs it into the venv in editable mode. Verify with:

```bash
py-sezgi/.venv/bin/python -c "import sezgi; print(sezgi.__version__)"
```

### Documentation site

The docs dependency group is declared in `py-sezgi/pyproject.toml`
(`[dependency-groups] docs`, pinned exact versions: `mkdocs==1.6.1`,
`mkdocs-material==9.7.7`, `mkdocstrings==1.0.6`,
`mkdocstrings-python==2.0.8`, `markdown-exec==1.12.3`,
`pymdown-extensions==11.0.2`, `matplotlib==3.11.1`). Install it into the
SAME venv used above (not a separate one — mkdocstrings needs the
already-built `sezgi` extension importable), then build:

```bash
uv pip install --python py-sezgi/.venv/bin/python \
  mkdocs==1.6.1 mkdocs-material==9.7.7 mkdocstrings==1.0.6 \
  mkdocstrings-python==2.0.8 markdown-exec==1.12.3 \
  pymdown-extensions==11.0.2 matplotlib==3.11.1
py-sezgi/.venv/bin/mkdocs build --strict
py-sezgi/.venv/bin/mkdocs serve   # local preview
```

`mkdocs build --strict` is a required gate on any change to `docs/site/`,
`mkdocs.yml`, or any file a doc page renders (public API docstrings,
example scripts referenced by a tutorial or figure script).

### R

```bash
R CMD INSTALL r-sezgi
```

`r-sezgi/DESCRIPTION` declares the same Rust-toolchain prerequisite
(`SystemRequirements: Cargo (Rust package manager)`) — no other system
dependency is required.

## The three gate commands

Every change that touches Rust, Python, or R source must leave all three
suites green before it is proposed:

```bash
cargo test --workspace --release                                  # Rust
cd py-sezgi && maturin develop --release && pytest                # Python
R CMD INSTALL --preclean r-sezgi \
  && Rscript -e 'testthat::test_dir("r-sezgi/tests/testthat", package = "sezgi")'  # R
```

A change confined to one language still runs its own gate; a change to
shared documentation or examples runs whichever gate(s) it touches, plus
the docs build if it touches `docs/site/` or anything a doc page renders.

## Conventions

- **English everywhere.** All documentation, comments, commit messages,
  and code artifacts in this repository are written in English, with no
  exceptions for draft or internal material.
- **No emoji** in commits, documentation, or code.
- **Run before commit.** Every documentation page's code snippet, every
  tutorial, and every example is executed — not merely written — before
  it is committed. Tutorials execute at `mkdocs build` time via
  `markdown-exec`; examples are exercised by their own pytest/testthat
  files; figures are generated by seeded scripts under `docs/scripts/`
  with data sidecars asserted by tests. Nothing is hand-typed and assumed
  correct.
- **Anchored, not eyeballed, examples.** Runnable examples end with an
  assertion (or an equivalent pinned-value check) on a value the run
  itself produced, so a regression in behavior fails a test rather than
  silently changing printed output.
- **Cross-language parity is a gate, not a goal.** Where a Python example
  has an R twin (or vice versa), the pair is expected to produce
  bit-identical results for the same seed; existing parity tests are
  never modified to make a change pass — if an edit breaks parity, the
  edit is wrong, not the test.
- **Deterministic by construction.** Every algorithm's behavior is fully
  determined by `(spec, problem, seed, budget)`. Contributions that add
  non-reproducible sources of randomness (wall-clock seeding, unseeded
  library RNGs, iteration-order-dependent floating-point accumulation)
  are out of scope.
- **Honest provenance.** A new algorithm preset names its source (the
  original paper, or the author's own reference implementation) and
  states plainly where sezgi's own implementation is a documented
  simplification rather than a paper-faithful reproduction. See
  `examples/README.md`'s catalog for the established format.

## Working in a worktree / opening a pull request

- Prefer a dedicated git worktree or branch per change rather than
  working directly on `main`.
- Keep pull requests scoped to one logical change; large migrations are
  expected to be split into a sequence of reviewable commits, each
  passing all applicable gates on its own.
- Describe, in the PR body, which of the three gates (cargo / pytest /
  testthat) and the docs build were run, and their result counts.
- `docs/DECISIONS.md` is the project's running record of architectural
  and scope decisions, milestone by milestone. A PR that makes a
  non-trivial design choice, or that closes or narrows a previously
  recorded deferral, is expected to add or update an entry there rather
  than leave the decision undocumented.
- See the [issue templates](.github/ISSUE_TEMPLATE/) for bug reports and
  feature requests, and the
  [pull request template](.github/PULL_REQUEST_TEMPLATE.md) for what a
  PR description should cover.
